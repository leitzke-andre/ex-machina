# USB-MIDI patch (emulator-tested and running on a real unit)

`tools/midi_patch/` turns the stock Mikro MK3 firmware (carved from NI's updater, see `docs/firmware-notes.md`) into a **class-compliant USB MIDI device** by patching seven places and adding about 3 KB of new code, config and descriptors. It is developed and tested in an ARM emulator (Unicorn, including the firmware's real USB library enumerating against a modelled USB peripheral and replays of real recorded reports), and **since 2026-10-17 it runs on a real Maschine Mikro MK3**: it enumerates as a USB-MIDI device on macOS and sends the expected notes, pressure and CCs, the display and LED feedback work, and the stock updater restores the original firmware (`docs/hardware-plan.md` has the log). It also works on an iPad Air 4 over USB-C (listed as MIDI input and output, pads play, strip is the mod wheel). Not yet checked: current draw. The third generation (local LED behaviour, MIDI Start/Stop for the transport buttons, pad base 36, a touch-strip LED, resting LEDs re-applied by a main-loop hook after the stock startup animation) was flashed on 2026-10-17 and works. The fourth generation adds a **run-time, savable configuration** (remapping over SysEx, `docs/remap-protocol.md`); it was flashed on 2026-10-18 and works: live remapping, saving, loading after a power cycle, rewriting and erasing the saved record were all checked on the device. Read "Open risks" before flashing a unit of your own.

## What it does
Defaults follow **NI's own MIDI-mode map** (Maschine Mikro MK3 manual, p. 75), so existing MIDI mappings made for NI's MIDI mode carry over.

| Direction | Behaviour |
|---|---|
| Pads (16) | Hit or press -> Note On, velocity from the curve table (default: the 12-bit value >> 5, as the community drivers do), min 1; release -> Note Off; pressure change while held -> Polyphonic Key Pressure on the same note (NI's template does the same: Hit sends the note, the Press action is Poly Pressure on that note; NI keeps streaming pressure without a held note, here it is sent only while the pad's note is on). Two more deliberate differences from NI's engine (decompiled, see `docs/research-sources.md`): NI ignores the firmware's PressOn/PressOff events (types 0/2) and plays a note only for a detected hit, whereas here a slow press that never registers as a hit still plays a quiet note; and NI reports the release as Note On with velocity 0, here it is a Note Off. **Velocity curve:** Note On velocity is looked up in a 256-byte table (index = 12-bit value >> (vel_shift - 1)), at least 1. The default is NI's own default, Linear, which is exactly `value >> 5` (what the community drivers send) and should be within one step of NI if its host normalises the 12-bit value linearly (not read). `--vel-curve soft3|soft2|soft1|linear|hard1|hard2|hard3|fixed` picks one of the presets of the Controller Editor's *Pad Velocity Curve* menu (formulas in `docs/research-sources.md`; `fixed` is the editor's constant-full slot), `--vel-table FILE` a custom curve (128 or 256 integers 0-127), `--vel-shift 1..8` the gain in front of it (smaller = more sensitive; also scales pressure). Pressure messages never go through the curve, as in NI's engine. Pad *n* (the number printed on the pad) sends note `base + n - 1`. *New:* **the default base is 36 (pad 1 = 36 ... pad 16 = 51)**, the General MIDI drum layout that GarageBand's and most iOS drum kits listen to (the manual's diagram labels these C1..D#2). NI's own template (the Controller Editor's Mikro MK3 "Pad Page A") uses 12-27, still available with `--pad-base 12`; that was the first default, and on the iPad the pads then played chromatically from C-1, below any drum kit. The HID pad index runs top-left first (index 0 = pad 13, index 12 = pad 1); the defaults account for it. |
| Buttons | (Report 1 is sent only when something changes, so even the very first one can be a press: buttons start from "nothing pressed", found on the real device.) Press -> CC 127, release -> CC 0 (gate) on NI's numbers, which the template's disabled entries confirm one by one: Project 38, Favorites 39, Browser 40, Volume 44, Plug-in 45, Swing 46, Sampling 47, Tempo 48, Pitch 49, Mod 50, Perform 51, Notes 52, Group 34, Auto 35, Lock 36, Note Repeat 37, Restart 53, Erase 54, Tap 55, Follow 56, Play 57, Rec 58, Stop 59, Fixed Vel 80, Pad Mode 81, Keyboard 82, Step 83, Chords 84, Scene 85, Pattern 86, Events 87, Variation 88, Duplicate 89, Select 90, Solo 91, Mute 92. NI's own map constructor creates no assignment for the arrows and Shift, so nothing is sent for them; here Left 41, Right 42, Shift 43. NI's default, in the template and in the editor's built-in map (decompiled: button mode 0, sent on press), is *toggle* (127 and 0 on alternate presses); `--btn-mode toggle|trigger|gate` selects it, gate is the default because it works with every DAW action. *New:* **transport** (`--transport realtime|cc|mmc`, default `realtime`): Play sends MIDI **Start** (`FA`) and Stop MIDI **Stop** (`FC`), on press only, because iOS apps and hardware sequencers answer those and know nothing of NI's CC 57 / 59 (on the iPad the transport buttons did nothing); Rec stays CC 58 (MIDI has no realtime record message). `cc` keeps NI's 57 / 58 / 59, `mmc` sends MIDI Machine Control (`F0 7F 7F 06 02 F7` play, `06` record strobe, `01` stop). Underneath, every button has an **action** in the config block (`btn_act`): CC (default), note (on while held, the note number in `btn_cc`), Start, Continue, Stop, MMC (the command in `btn_cc`) or none; this is what the planned remapping will edit. |
| Encoder | Rotation -> CC 7 (the stock 4-bit counter counts **up** when the knob is turned clockwise, measured with a clockwise-only recording, so clockwise raises the value as in NI's engine), press -> CC 8 (the manual's diagram; NI's Mackie template re-assigns the push to CC 15), touch -> **CC 9** (NI's template default). Rotation is **absolute 0-127 starting at 0, no wrap** (the template's `wheel`: min 0, max 127, default 0, wrapmode 0; at a limit nothing is sent: NI's `Assignment::incValueInt` returns without a message when the clamped value did not change); config selects NI's other Control Change modes: relative-offset (65 / 63 around 64) or relative (1 / 127); `--enc-mode`, `--enc-init`. |
| Touch strip | CC 1 = 0-127 from the finger position (measured on the stock device: left end 1, right end 200, 0 = untouched; a slide gives about 80 samples). Optional CC 0 on release. |
| Local LEDs | *Like NI's MIDI mode (editor manual): assigned buttons rest dimly lit (`0x7C`) and light up bright (`0x7F`) while pressed (in toggle mode: while on); the 16 pads rest in one colour (default blue, `--pad-colour 1..17`, 17 = white) and flash bright while hit; the touch-strip LED under the finger lights up (25 LEDs for the 200 positions, white, `--strip-colour`).* `--local-leds off` disables it all. The encoder press and touch have no LED. **The stock startup ends by clearing every LED** (found on the real device: the resting frame written at boot was gone until the first interaction; reproduced in `test_startup.py`): a fade-in animation drives the LED matrix directly and its last steps leave every cell dark, and the stock loop does not look at the LED buffer again. So the boot hook only prepares the resting frame, and the **main-loop tick hook writes it out once, as soon as the startup countdown (struct+2, 6000 ms) has reached 0**; LEDs a host sets during the animation are written out again then too. During the animation the LED matrix is identical to stock. |
| Host -> device: LEDs | The firmware keeps a **shadow of every LED it was told about and rewrites the complete state** on each message (the stock loop clears its "frame pending" flag first and then reads the 80 entries, so a partial frame can be wiped by a packet that arrives mid-pass; see `test_led_race.py`). Channel 2, note *n* (0-79) drives LED *n* directly. Channel 1: the pad's own note lights that pad; the CC a button sends lights that button (0 off, < 43 dim, < 86 normal, else bright). Note velocity is the firmware's colour code (colour = vel >> 2, brightness = vel & 3); velocity 0 or Note Off = off. SysEx `F0 7D 4D 4B 02 <80 bytes> F7` sets all 80 LEDs. *New:* a LED the host sets becomes that LED's **resting colour** (a local press or hit returns to it, off included). CC feedback matches only buttons whose action is a CC: with the default transport, CC 57 / 59 no longer light Play / Stop (use notes 22 / 24 on channel 2, or `--transport cc`). |
| Host -> device: display | SysEx `F0 7D 4D 4B 01 x page w-1 h-1 <7-bit packed pixel bytes> F7` writes a region of the 128x32 display (seen working on the device: a border with diagonal ticks drawn upright, top-left to bottom-right). **Pace the regions** (>= 10 ms apart, as `mmk3_host.py` does): the stock loop clears the display flag and then copies the staging buffer, so a region that arrives while the previous one is still pending is dropped, and one that arrives mid-copy could corrupt it (not reproduced yet). |
| NI's own protocol | Output reports 0x80 / 0xe0 / 0xf3 / 0xf4 still reach the stock parser, but with a bulk MIDI endpoint stock NI software cannot reach the device anyway. |
| USB | Device class 0; interface 0 Audio Control, interface 1 MIDI Streaming (bulk OUT 0x01 / IN 0x81, 64 B, one cable), interface 2 DFU runtime (kept, so DFU_DETACH still reboots into the bootloader). VID:PID `17cc:1700`, bcdDevice `0x0051`, 480 mA requested (all three are build options). |

The **defaults** live in a 274-byte config block at flash `0x0800CE00` (`struct cfg` in `translate.c`, mirrored by `default_cfg()` in `mmk3_config.py`, size checked at compile time): channel, pad notes, button CCs and mode, per-button actions, encoder/strip CC, encoder mode and start value, velocity shift, LED channel, pad-to-LED map, the local-LED flags and colours (buttons, pads, strip), optional pad sensitivity and boot delay, and, since the fifth generation, the velocity curve, the Fixed Vel value, the Keyboard root, the pad pressure mode a **second (shifted) action per button**, and (phase 2) the scale, chord type, the three encoder target CCs, and (phase 3) the arp pattern, rate, octaves and the start tempo. The firmware works on a **RAM copy** of that block, which starts as the defaults or as the config saved in flash, and which a host edits with SysEx (INFO / GET / SET / SAVE / RESET, `docs/remap-protocol.md`; `tools/midi_patch/mmk3_config.py` is the command line and the library). A SET is checked, then active at once; SAVE keeps it across power cycles in the flash page `0x0801EC00`.

## The controller's own functions (fifth generation; built and emulator-tested 2026-10-18, flashed: see `docs/hardware-plan.md` step 6)
The patch reproduces the pad modes and a few helpers of NI's own controller, independent of any software (`docs/native-features.md` has the review of the manual). They are **button actions** in the same mapping table (`ACT_PADMODE` ... `ACT_SHIFT`, `docs/remap-protocol.md`), so a preset can mix them with plain CCs; the preset *Maschine-like modes* assigns them to the buttons printed with those names.
- **Pad Mode** (Group): the pads play the configured pad notes (drum layout, default 36-51). **Keyboard**: pad 1 = `keys_root` (C3 = 60), chromatic upwards, left to right and bottom to top (pad 16 = root + 15). **Fixed Vel**: every Note On at `fixvel` (127). **16 Velocities** (Shift + Fixed Vel in the preset): every pad plays pad 1's note (or the root) at velocity 8, 16 ... 127. Fixed Vel and 16 Velocities exclude each other. **Transpose** (arrows: a semitone, with Shift an octave): added to every pad note, clamped to 0..127, at most +63 / -64 in total.
- **Velocity curve** (Shift + Volume next, Shift + Swing previous): the eight curves of NI's editor and a ninth custom slot; the choice is applied at once and **kept across power cycles** through the settings log (`docs/remap-protocol.md`). **Panic** (Shift + Mute): All Sound Off and All Notes Off on all 16 channels (32 messages, sent from the main loop as the TX ring has room); the held pads are forgotten.
- **Shift layer**: any button can be set to *Shift (hold)*; while one is held, a button whose `btn_act2` is set does that instead, otherwise its normal action. The layer is chosen when a button goes **down** and the release uses the same one (so releasing Shift first does not leave a CC stuck). A Shift pressed in the same report as another button counts for it. While a button is held its note is remembered per pad, so a Note Off always follows its Note On even if the mode or the transposition changed in between.
- **Scales and chords** (phase 2): Keyboard mode plays the scale of `scale` (24 of them, 12-bit masks in flash: chromatic, major, the modes, harmonic and melodic minor, pentatonics, blues, whole tone, both diminished, Hungarian minor, Phrygian dominant, double harmonic, Hirajoshi, In-sen, major blues, bebop dominant, Neapolitan minor): pad *k* = root + the *k*-th scale degree, the octaves continue. **Chords mode** (a third pad mode): pad *k* plays the chord built on scale degree *k* by stacking scale degrees (triad 1-3-5, seventh 1-3-5-7, sus2 1-2-5, sus4 1-4-5, power 1-5); on the chromatic scale the chords are built on the major scale. Three more types are **fixed shapes** on the pad's scale note, whatever the scale: minor (root, minor third, fifth), maj 9 (1 3 5 7 9 with the major seventh) and maj 11 (1 3 5 7 9 11); so in C major pad 2 plays D minor as triad, and D F# A C# E as maj 9. Each held pad remembers its notes (up to six), so a chord pad is always released with the notes it started, and pressure goes to its root. Shift + Keyboard / Pad Mode step the scale, Shift + Chords / Select the chord type. Because a chord hit is up to 12 packets (a maj 11 retriggered: six Note Offs and six Note Ons), the translator hands its output buffer to the TX ring whenever less than 48 bytes are left (the stock enqueue copies at once and its return value is unused), instead of refusing reports.
- **Strip modes**: Pitch (the whole strip is a bend over 14 bits, back to the centre 8192 when the finger leaves), Mod (CC 1, holds its value after release, the value shown as a dim bar on the 25 strip LEDs with the finger LED on top; the bar is cleared when another mode is chosen), Perform (the configured `strip_cc`, as before). **Encoder targets**: a button set to *Encoder target* points the encoder at CC 7 / 10 / 11 (configurable) with an absolute value per target starting at 64, shown on the screen (`CC 7 / VALUE 65` and a bar); the same button again goes back to the configured encoder CC and mode. **Program Change**: next / previous / back to 0 with the number on the screen.
- **The grid, tap tempo, MIDI clock** (phase 3): 24 pulses per beat, from the internal tempo (default 120 BPM or the config's) or from an incoming MIDI clock. The internal grid is the stock millisecond counter times 1000 added into a microsecond accumulator, one pulse per 2,500,000 / BPM microseconds (about 1 ms of jitter, the main loop's pass time; at most 8 pulses are caught up after a stall such as a flash write, then the accumulator restarts). It only runs while something needs it (an arp with notes, the clock output); an incoming clock runs it whenever pulses arrive. The USB interrupt only **counts** realtime bytes (Clock, Start / Continue, Stop, a free-running byte each, so the main loop's read cannot race it); the main loop turns them into pulses. An external clock is "present" while a pulse arrived within 400 ms; then it replaces the internal timer, Start restarts the grid, Stop closes the arp's note, the clock output does not echo it, and tap tempo says EXT CLOCK. **Tap tempo**: the mean of the last three taps, a pause over 2 s starts a new run, limited to 20..275 BPM; the tap button blinks on the beat (bright for 6 pulses) while the grid runs. **Clock output** (Shift + Tap in the preset, default off): MIDI Start on switching on, then 0xF8 on every pulse, Stop on switching off; since it is a second clock master, it is never on unless asked for.
- **Arp and Note Repeat**: with the arp on, a pad hit adds its notes (up to 16 entries, with the hit velocity) to a list instead of playing them; the list plays one step per grid step (`arp_rate`): *repeat* all held notes at once (NI's Note Repeat), *up*, *down*, *up-down* (ends not repeated), *played* (press order) and *random* (a 16-bit LCG) through `arp_oct` octaves (notes above 127 are skipped). A note is released half a step after it started. The first note of a new chord starts the grid and sounds at once; when a clock (external, or the clock output) is already running the first step waits for the grid. **Latch** keeps the list after the pads are released until the next pad hit with nothing held. The arp is silent for muted pads, works in every pad mode (the notes are whatever the pad would play: chords arpeggiate), and a pad held when the arp is switched on keeps its own note and is released with it.
- **Mute and solo pads**: *Mute* / *Solo* switch an edit mode in which a pad hit toggles that pad's mute or solo bit instead of playing; muted pads (and, while any pad is soloed, the others) are silent and rest dark, soloed pads rest brighter; *Clear* resets both. Part of the run-time state: gone after a SET or power-up.
- **Strip strum**: strip mode 3 divides the strip among the notes of the pads held now (ascending), else the first note of each of the 16 pads; moving into a zone releases the previous note and plays the new one at velocity 100, letting go releases it. **Snapshot** (*Lock*): stores the three encoder target values, the mod wheel value and the encoder's own value, and on the next press sends them back as CCs (so the host's controls jump back); a second action stores again.
- **MIDI channel** (Group / Shift + Group in the preset): steps the channel 1-16 on the device; the notes on the old channel are released (the panic burst, 32 messages), and the choice is kept across power cycles in the settings log (kind 2) without saving the config. **Preset slots**: four configurations in the device's flash (pages `0x0801D800` to `0x0801E400`, one record per page, the same record as the saved config), stored and loaded with buttons (Scene / Pattern / Events / Variation, Shift stores) or with SysEx (`15` store, `16` load, `17` list). Loading makes the slot the active config (not the power-up one; SAVE does that). A store erases and rewrites one page: a power cut leaves the old, an empty or the new record, never garbage, and no other slot is touched (`test_phase4.py` cuts at every flash write). The records are built in the reply buffer, not on the stack.
- **Step sequencer**: Step mode (a fourth pad function) makes pad *n* step *n* of the selected track: a hit steps it off, normal, accent; the pad LEDs show the track (dim off, colour on, bright accent) and the playhead in white; the selected track is picked with Select held + a pad (the 16 tracks are the 16 pad notes of the drum layout). Four patterns of 16 tracks x 16 steps (2 bits per step, 256 bytes of RAM), selected with Plug-in / Sampling; the sequencer starts and stops with Shift + Step and runs on the same grid as the arp, at 1/16 steps, following the internal tempo, the tap tempo or an incoming MIDI clock (with no grid running it starts the grid and its first step sounds at once, else it waits for the next step boundary); notes are 100 (normal) or 127 (accent) and released half a step later; muted pads silence their track; Erase clears the track, Shift + Erase the pattern, Restart goes back to step 1, **Shift + Restart keeps the patterns in their own flash page** (loaded again at power-up; a cut during the save leaves a whole old record or none). The screen shows the **grid** (16 cells of 8 pixels: a small bar for off, a tall bar for on, a taller one for accent), a top line (`TRK 1 C1 PAT 1 RUN`), the playhead and beat marks.
- **Per-button CC mode, pages, acceleration** (generation 10): every button that sends a CC can have its own mode (gate / toggle / trigger; `btn_mode_ovr`, 2 bits each, 0 = the global one), so a toggle for a mute and triggers for a bank step can sit side by side (the toggle LED shows the state). *Pad page* (action 40) moves the drum pads up by 16 notes per page (8 pages, wraps, a message `PAGE 2/8 E2-G3`; the Keyboard layout does not move; notes stop at 127), which gives a 16-pad controller the 64 pads of an app that maps pad *n* to note *n*. *Encoder page* (action 41) moves the three encoder targets to the next group of CCs: on page *p* target *t* sends `enc_tgt_cc[t] + enc_page_step × p` (`enc_pages` 1..8; a CC past 127 sends nothing), each page remembers its own value, and a snapshot remembers the page it was taken on. `enc_accel` 1..3 makes a fast turn take bigger steps (*n* → *n* × (1 + accel × (*n* − 1)), at most 40). Test: `test_phase5.py`. The **BeatMaker 3 (draft)** preset puts these to use (untried).
- **Slot buttons**: **Project** (top left, away from the pads) loads the next slot that holds a config, 1 → 2 → 3 → 4 → 1, skipping empty ones (ACT_SLOT parameter 8); the screen shows the slot and its name. The current slot is the one last loaded or stored (by a button or the host); after a power-up or a config from the host it is the slot whose config is the active one, else the cycle starts at slot 1. **Project is fixed to this, with and without Shift, in every config**: the firmware sets it on every config that enters RAM (the defaults, the saved one, a slot, one from the host: `cfg_fixed()`), the tools put it in every config they make (`mmk3_config.fix_project()`, `fixProject()` in the page), the page shows it greyed out and the CLI refuses to remap it. So a config can never lose the way to the other slots. (Program Change back to 0 moved to Shift + Browser in *Maschine-like modes*.) Until 2026-10-20 Scene / Pattern / Events / Variation loaded slots 1-4, which was too easy to hit while playing; they are plain CCs again (ACT_SLOT 0..3 still loads one slot directly in a custom mapping). Slots stored before that change get Project fixed when they are loaded. No shipped preset stores from a button: an earlier version had Shift + the button store in *Maschine-like modes*, which overwrote three slots with that preset when the same Shift gesture was used to load (storing is *Store current* in the tool, `slot store` in the CLI, or a custom ACT_SLOT 4..7 mapping). A loaded app preset leaves most buttons dark and silent because only the buttons the preset assigns are lit and active.
- **Slot names**: a slot keeps a name (up to 20 characters, the preset's **display name**, set by the host with SLOT STORE, shown by the browser tool next to the slot). Loading the slot with a button shows `SLOT 2` and the name on the screen instead of `LOADED`; a slot stored without a name shows `LOADED`. The device remembers the name of the last slot loaded or stored, so Shift + a slot button stores under that name; a SET, RESET or any other new config forgets it. Test: `test_phase4.py`.
- **Pad pressure**: polyphonic aftertouch on the sounding note (default), channel pressure, a CC, or off; the two single-value modes send 0 when the last pad lets go.
- **Mode LEDs**: a button that selects a mode is lit while the mode is on (Pad Mode at start), at rest otherwise, even with local lighting off. The modes are run-time state: they start fresh at power-up and after every SET; only the curve is kept.
- **Screen**: the idle screen is ours: **EX-MACHINA** at twice the size, a detail line (the version, `V0`, from `mmk3_config.FW_VERSION`, **or the names of the notes sounding**) and a status line (`DRUMS CH1 120`: pad mode, MIDI channel, tempo, and ARP / CLK / SEQ while they run). **Notes on the screen**: while notes sound, the detail line shows their names, lowest first (middle C = C3): a pad's note, **every note of a chord pad**, several pads together, and what the arp, the sequencer and the strum sound; with more than five notes the first four and `+n` (`C3 D3 E3 F3 +4`). They stay for half a second after the last one stopped, so a short note is readable, then the version comes back; a message takes the screen first and the notes return after it. A change shows a **message** for 1.5 s (title at twice the size, a detail line, sometimes a bar: `KEYBOARD / C3-D#4`, `FIXED VEL / ON  127`, `VELOCITY / HARD 1`, `SLOT 2 / SAVED`, `CHANNEL / 3` ...) and then the idle screen is drawn again; in step mode the picture behind the messages is the **sequencer grid** instead (below). The firmware no longer copies NI's picture from the framebuffer and restores it (generations 5-7 did): the picture is drawn from state, so it is always right, no image of NI's is stored, and 512 bytes of RAM are free. A screen column is a 32-bit mask (`col_msg` / `col_idle` / `col_seq`), cut into the two 256-byte halves (pages 0-1, 2-3) the stock staging buffer takes; the text is the 5 x 7 font (upper case), the title the same at twice the size. The write happens in the main loop with interrupts off (about 0.15 ms) and only while the stock "display pending" flag is clear **and the stock sender is idle** (a region applied while NI's code is still sending the previous one makes it flicker a bar at the bottom right of the screen: `docs/firmware-notes.md`), so a picture takes two regions of about 8 main-loop passes each; whatever changes what the picture shows (`view_sig`: pad mode, channel, tempo, arp / clock / sequencer state, the sequencer's playhead and edits) marks it dirty. A host's SysEx display region still works and stays until the next redraw.
- Tests: `test_phase4.py` (the channel, slots, the sequencer, its grid and the idle screen; every flash write cut) and `test_phase3.py` (96 checks, time-based: the clock output at 48 pulses a second and evenly spaced, tap tempo at four speeds, every arp pattern, rate and octave against hand-computed sequences, latch, external clock including the fall-back and Start / Stop, mute / solo with the LEDs, strum, snapshot, the screen messages) and `test_phase2.py` (64 checks: all 24 scales and 8 chord types against an independent model, a chord report of 21 hits with the output flushing, strip modes and their LED bar, encoder targets and their limits, Program Change, the new screen messages) and `test_modes.py` (82 checks: notes and velocities in every mode, a pad held across a mode change, the shift layer including the release order, the curve selector and its log with a power-cut sweep, panic with a nearly full ring, pressure modes, mode LEDs, and the display compared **pixel by pixel** with an independent reference, including the restore, a second message and a message during the restore). The stock display routine (staging copied into the framebuffer, flag cleared) is modelled in Python; it was read from the disassembly of `0x08003f34`. `test_display_race.py` injects a host display region (the real USB handler) at every point of the ticks that write a half of a message or of the restore, honouring the emulated PRIMASK: whatever the stock loop is handed is always a whole known region (a mutation check, the masking removed, makes it fail at nearly every cut point).

## Host mode for DAW scripts (generation 11; built and emulator-tested 2026-10-21, not flashed)
Two SysEx commands let a script in a DAW own the screen and read the pads as a grid (`docs/remap-protocol.md`; the FL Studio script in `integrations/fl_studio/` uses them, `docs/fl-studio.md`). **HOST** (`20 <flags>`, answered with `60`): SCREEN makes the picture behind the messages the host's four text lines instead of the idle screen / sequencer grid (`col_host`, the same 5 x 7 font in 21 cells per line; `view_sig` then only follows the text), RAW makes every pad send note 36 + its number - 1 whatever the pad mode, arp, mute / solo or step edit mode (a pad's Note Off follows the way its Note On went, `rawheld`; everything the pads hold is released when RAW changes), QUIET suppresses the firmware's own messages (`m_show`). **TEXT** (`21 <line> <column> <characters>`) is stored by the USB interrupt and drawn by the main loop like any picture (two regions; a TEXT that arrives in the middle of a write leaves the next redraw due, `test_host.py` interrupts the write at every point). Host mode is RAM only: power-up clears it, and so does a SET / RESET / slot load from the host, so a DAW that quit without saying so cannot leave the device in it once another tool takes over; the Project button's slot change keeps it. With SCREEN on, the device's own messages (Keyboard, scale, Fixed Vel ...) still show for 1.5 s and the host's text comes back after them. Cost: about 1.2 KB of code, 90 bytes of state. Test: `test_host.py`.

## Robustness (the adversarial review of 2026-10-20)
Findings of a four-part review (USB stack and boot, configuration and flash, the playing runtime, the flasher), each fixed with a test that fails on the firmware before it (`test_review.py`, and new checks in `test_hal_usb`, `test_features`, `test_safety`, `test_phase2`, `test_native`, the flasher's tests):
- **The transmit ring takes whole packets only.** It holds 0x4FF bytes, not a multiple of 4: when a host stopped reading, the last packet was cut and every later one shifted, garbage until the next power cycle (NI's enqueue in the patched image did the same; it is now handed whole packets). The ring is also emptied of what was queued before a bus reset or a new configuration (only that: the interrupt records where the ring ended, the main loop drops up to there).
- **Notes are counted.** A Note On always goes out, a Note Off only when no other source holds the note (overlapping chord pads, 16 Velocities, a pad and the sequencer on the same drum, chord notes clamped to 127). **Another config taking over** (a slot, SET, RESET) first releases everything that sounds with the config it was started with: held pads and chords, held note buttons, the arp, the sequencer (which now remembers its notes), the strum note, the pressure and a bent pitch. A bent pitch also goes back to the centre when the strip leaves Pitch mode, the channel changes or on panic.
- **Clock**: the external clock is forgotten 400 ms after its last pulse (the 16-bit timeout wrapped every 65.5 s and briefly stopped the internal clock); an arp phrase no longer restarts the grid under a running sequencer; the tap tempo's pause is checked every pass; clock out sends no Start / Stop while an external clock runs; a 16-note arp plus 16 sequencer tracks in one pulse no longer overflow the clock's buffer.
- **Config and flash**: a full settings log bakes the curve and channel into the *saved* config (it used to save whatever was active, a slot or an unsaved SET); the Project cycle and SLOTS skip a slot this firmware would refuse, and after a power-up match the slots ignoring only the logged curve / channel; NOTE and MMC buttons need their number (0xFF went out as a status byte); a SLOT STORE's name is staged and taken over by the main loop (the interrupt wrote the main loop's slot name); RESET reports unsaved changes when the log will apply at the next boot; the flash controller is unlocked only when locked; PEEK no longer allows the reserved flash-interface words.
- **USB**: SET_INTERFACE resets endpoint 1 to DATA0; a halted IN endpoint is never re-armed by the transmit path (and arming happens with interrupts off); CLEAR_FEATURE(HALT) on endpoint 0 succeeds; DFU GETSTATUS / GETSTATE report appDETACH after a DETACH, and a bus reset after DETACH goes into DFU mode; a reboot (1C flag 4) and HANG wait until their reply has left the device (`Device.hang()` sends it once).
- **Standalone image**: its reset handler sets the stack pointer itself (NI's bootloader's stack sits just above the transmit ring); the stub for NI's display fade and settings save is no longer called.
- Not changed: the USB suspend still keeps the pads and LEDs running for 0xFFF0 main-loop passes (the current draw needs measuring first).

## How it hooks the stock firmware
All analog scanning, pad linearisation, peak detection, debouncing and the strip I2C code stay untouched. The patch sits after them:

| # | Address | Stock | Patched | Purpose |
|---|---|---|---|---|
| 1 | `0x08004036` | `bl 0x08008a38` (enqueue HID reports into the 0x500-byte TX ring) | `bl mmk3_translate` | Parse report `01` (14 B) and `02` (64 B) and enqueue 4-byte USB-MIDI packets into the **same** ring; the stock EP1 sender drains it unchanged. This is the only call to the enqueue routine. |
| 2 | `0x08008cf8` | `bl 0x08007ea2` (board init) | `bl mmk3_init` | Zero the translator state, repoint the RAM descriptor table (`0x20000080`) at the new descriptors, then call the original init |
| 3 | `0x08008cfc` | `bl 0x08008bac` (stage-2 init) | `bl mmk3_boot2` | Call the original; optionally override pad sensitivity (re-running the stock threshold routine) and the startup period (stock: ends after the LED fade-in, 6 s at most); then prepare the resting state of the local LEDs (in the shadow only, see hook 7) |
| 4 | `0x08004aba` | `bl 0x08008798` (host OUT report parser) | `bl mmk3_rx` | Handle MIDI packets (first byte < 0x10): notes, CCs, SysEx; forward everything else |
| 5 | `0x08008526` | `asrs r1,r5,#3` (EP1 type 0x600 = interrupt) | `movs r1,#0` | EP1 becomes bulk |
| 6 | `0x08008460` | interface check accepts only interface 0 | accepts 0-2 | SET_INTERFACE for the MIDI and DFU interfaces |
| 7 | `0x08008d06` | `bl 0x08005414` (watchdog kick, first call of every main-loop iteration) | `bl mmk3_tick` | Call the stock kick, then: once, when the startup countdown has reached 0, write the LED shadow out again; handle a pending configuration request (SET / SAVE / RESET, the flash write included) and send a pending reply into the TX ring. Everything that must not run in an interrupt |

New flash: config `0x0800CE00` (274 bytes, 288 reserved), device descriptor `0x0800CF20`, configuration descriptor `0x0800CF40`, the velocity tables `0x0800D000` (nine curves of 256 bytes: NI's eight and a custom slot) with a count byte at `0x0800D900`, the display font `0x0800D940` (5 x 7, ASCII 32-95) and the display texts `0x0800DA80` (16 bytes each, room for 192), the scale masks `0x0800E6C0` (24 x 16 bits), code `0x0800E700` (23,418 bytes; **last**, so it can grow up to `0x0801D800`, about 39 KB more); the image ends at `0x0801427A` (70,266 bytes). Above the code: the four preset slots `0x0801D800` / `0x0801DC00` / `0x0801E000` / `0x0801E400`, the step patterns `0x0801E800`, the save page `0x0801EC00`. The saved configuration lives in the flash page `0x0801EC00` (outside the image, below the stock settings pages). Translator, LED shadow, SysEx and configuration state (2,776 bytes of the 3,584 available: output buffer 512, SysEx 320, LED shadow and resting layer 80 each, two config buffers, the staged config and the reply buffer, the mode state, the display message, the 256-byte step patterns) live in RAM at `0x20004200` (`ST_ADDR` in `translate.c`; `build_patch.py` reads the address from there and checks the other layout constants against the C source); the output buffer is protected by a per-report worst-case check (`test_features.py`). Stack use of the patched paths is 680 bytes worst case against a 1 KB stack (`stack_depth.py`, which now also runs a mode button through the display and panic paths).

## Display and LEDs
Both are driven by the stock firmware from RAM buffers filled by host OUT reports; the patch fills the **same buffers** from MIDI.

**LEDs** (index map confirmed by the firmware tables, three community drivers and, on 2026-10-17, a real unit: LEDs 0, 3, 8, 14, 22, 25, 26, 29 and 38 lit Project, Volume, left arrow, Group, Play, Shift, Fixed Vel, Chords and Mute; the 16 pad colours lit in the palette order below; CC feedback of 127 / 64 / 20 gave bright / normal / dim button LEDs). `FUN_08005490(index, code, ...)` sets one logical LED:

| Index | Count | Type | Meaning |
|---|---|---|---|
| 0-38 | 39 | mono | button LEDs; **LED index = button id** (same order as the input report bits) |
| 39-54 | 16 | RGB + white | pad LEDs; **LED 39 + pad report index** (same top-left-first order as pad events) |
| 55-79 | 25 | RGB | touch-strip LEDs, left to right |

Colour code = `colour * 4 + brightness`: colour 1 red, 2 orange, 3 light orange, 4 warm yellow, 5 yellow, 6 lime, 7 green, 8 mint, 9 cyan, 10 turquoise, 11 blue, 12 plum, 13 violet, 14 purple, 15 magenta, 16 fuchsia, 17+ white, 0 off; brightness 0-3 (0/1 dim, 2/3 bright). Buttons are mono: any non-zero colour works, the community drivers use 0x7c / 0x7e / 0x7f for dim / normal / bright. The LED chips sit behind a bit-banged I2C bus (addresses 0xE8 and 0xEE, IS31FL3731-style). `tools/emu/emu_led.py` confirms the decode against the stock routine.

**Display**: 128 x 32, 1 bit per pixel, 4 pages of 8 rows. A report is `x, page, w, h` (u16 each, only the low byte used) plus up to 256 pixel bytes; the stock code copies the region into a 128 x 4-page framebuffer and streams it over SPI2 with DMA. A byte is one column of 8 vertical pixels (bit 0 = top row of the page) and **a lit pixel is a cleared bit** (0xFF = blank): three community drivers agree. The patch writes the header/data to RAM `0x200013A1`/`0x200013A9` and raises the stock flag (`0x200012F8`); a new SysEx region is dropped while one is still pending.

`tools/midi_patch/mmk3_host.py` builds the messages (`led_frame`, `display_region`, `bitmap_to_messages`) and has three demos (`probe`, `border`, `colors`) for a first hardware session.

**Measured pad response** (stock device, 103 real hits recorded 2026-10-17, `tools/hid_capture.py`): the note-on peak value the firmware reports spans 416-4095 (median 2504, 25-75 % 1945-3003, 90 % below 3260), i.e. velocity 13-127 at `>> 5` (median 78, typical hard hits 94-103; 127 needs the hardest hits). 100 of 103 hits arrive within 10 ms of the first touch event (median 6 ms: the stock detector waits for the peak), a hit is held 83-826 ms (median 129). Touches that never became a hit peaked at 472 or less. Slow presses never produced a note-on: the firmware sends press-on at a value of about 288 (287-308, velocity 9) and the pressure then climbs, up to 4095, until press-off. Read against the emulator's table (raw 3000 -> velocity 17, 3900 -> 102) this implies that real finger hits peak near raw 3800-4000, the top of the 12-bit ADC range (an inference; the raw ADC values were not recorded).

## Staged images for the hardware day
`build_patch.py --stage 1|2|3` produces a ladder where each step changes one risk factor (details in `docs/hardware-plan.md`): 1 = stock image with only bcdDevice lowered (one byte); 2 = stage 1 plus the new flash content appended but unused (size acceptance); 3 = the full patch.

## Not built yet

## Open risks
1. **Bootloader acceptance** (hardware only). The updater sends the image raw through standard DFU (`DFUDevice::writeImage(image, 0x9dc8)`), with no host-side header or CRC, but the bootloader (0x08000000-0x08002FFF, not in any file we have) may still check size, CRC or a signature. The stage ladder isolates this.
2. **Recovery.** NI's updater is no longer the only way back: a verified copy of the stock image is kept and `tools/restore_stock.sh` / the browser tool flash it with our own DFU client (macOS is about to stop supporting NI's updater; the restore drill was run on the device on 2026-10-18 and works). Kept on purpose: the DFU interface and DFU_DETACH (verified in the emulator), the stock VID:PID `17cc:1700` (NI's updater only recognises that pair, DFU mode being PID `0x1702`), and bcdDevice `0x0051` (the updater offers an update only when bcdDevice < `0x0052`, so the stock firmware can always be put back). A device left in DFU mode by an interrupted update is a known recoverable state (NI's own support article and forum threads). **No re-entry path is known if a flashed app hangs before USB comes up** (only a debug probe would help), which is why the ladder starts with images that change nothing behavioural.
3. **Real pad range.** Thresholds derive from the stored sensitivity (ROM default 80); sensitivity, gain and curve are tunable (`--sens`, `--vel-shift`, `--vel-curve`), and the real range is now measured (see above): hits reach 4095 and the linear mapping needs no change; if a softer feel is wanted, `--vel-curve soft1` or `--vel-shift 4` (hits above 2048 then give 127).
4. **Power on iOS.** The descriptor asks for the stock 480 mA. A Lightning iPad without a powered camera adapter offers about 100 mA and shows "requires too much power"; USB-C iPads and powered adapters should be fine. The real current draw is unmeasured (`--max-power` changes only the declaration).
5. **NI host software conflict.** With VID:PID `17cc:1700`, NI's agents (if installed) may try to talk HID to a device that no longer has that interface. Use other IDs (`--vid/--pid`) if that becomes a problem, at the price of the stock updater no longer finding the device.
6. **NI's *fixed* MIDI mode versus the editor's template.** The pad notes, button CCs, encoder CCs and range come from the Controller Editor's Mikro MK3 template and agree with the manual diagram, the forum reports and, since the editor's own code was decompiled, with NI's built-in map (`MaschineMikroMK3::Map::Map` creates the same 36 button CCs, CC 7/8/9 for the encoder, CC 1 for the strip and velocity-curve property 3; toggle is the default button mode). The velocity curve is settled too: curve 3, NI's default, is **Linear** (`PadControl::calcPadVelocity_f`), so this patch's plain `value >> 5` should agree with NI to within one step (assuming the host normalises the 12-bit value linearly; that step was not read). What stays unobserved is whether the stock device with no editor running behaves exactly like that built-in map; recording the stock device on the hardware day would settle it.
7. **Resting LEDs and the startup animation.** The first flash of this feature showed the stock animation wiping the resting state; the tick hook re-applies it when the startup is over. Emulator-proven against the stock code (`test_startup.py`), not yet seen on the device. The stock startup in the emulator is shorter (about 1.7 s) than the 6 s countdown: it ends the countdown itself, so the resting LEDs should appear after about two seconds, not six.
8. **Transport defaults.** MIDI Start / Stop are what iOS apps and hardware sequencers respond to; a DAW that wants CC 57 / 59 or MMC needs `--transport cc|mmc` (and, later, a remap). Not yet seen on hardware.
9. **Flash writes on the device.** The save uses the firmware's own ST routines on a page nothing else touches, in the main loop, with the watchdog at about 1 s; the page took writes, rewrites and erases on the real chip (2026-10-18), so it is not write-protected. A real power cut during a save is not tested on hardware (the emulator cuts it at every flash write); it loses the saved config and the defaults load next time.
10. **Interrupt-context call**: `mmk3_rx` runs in the USB interrupt like the stock parser and only fills buffers and raises flags; a race with the main loop mirrors stock behaviour and is not stress-tested.
