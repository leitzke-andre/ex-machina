# Hardware day plan (not started)

Everything below is for when the device is connected. Nothing in this repository has flashed or probed hardware yet. The point of the ladder is that each step changes exactly one risk factor, so a failure tells you what failed.

## Before touching anything
1. Keep the stock firmware: the 40,392-byte image carved from NI's updater (`tools/carve_fw.py`). Its SHA-256 (carved from the v1.20 Mac updater): `76ebf72d33961639a0bd042ba32354dd8dc07569be69175546eb9fc06e5c5917`. NI's updater remains the restore path as long as the device reports bcdDevice < `0x0052` or is in DFU mode.
2. Build the images: `tools/midi_patch/run_tests.sh stock.bin work/` (all suites must pass) gives `work/stage1.bin`, `stage2.bin`, `patched.bin`.
3. Have: a USB power meter (current is the biggest unknown), a host with `pip install pyusb` and libusb, a MIDI monitor, a USB-C iPad or a powered Lightning camera adapter for the iOS test. Do not open the case at this point; nothing here needs it.

## Step 0: observe the stock device (read-only)
- `system_profiler SPUSBDataType` (macOS) or `lsusb -v -d 17cc:1700` (Linux): save the output. Expect VID 17cc, PID 1700, bcdDevice 0x0052, interfaces HID + DFU, 480 mA request, HID report descriptor 495 bytes (compare with `docs/firmware-notes.md`).
- `python3 flasher/dfu_client.py info`: shows the DFU interface, attributes `0x09` (can download, will detach), transfer size 64.
- Power meter: idle, with LEDs lit, pads pressed. Note the real current against the 480 mA declared.
- Optional, if you have NI's software installed: put the stock device in MIDI mode (SHIFT + Project) and record it with a MIDI monitor. The Controller Editor's Mikro MK3 template and its decompiled MIDI engine already settled the pad notes (12-27), the CC map, the toggle default and the encoder defaults (absolute from 0, nothing sent at a limit); the velocity curve is known too (NI's default, curve 3, is Linear); what remains is whether the stock device's behaviour with no editor running matches the editor's built-in map. A useful recording: strike one pad at several strengths and note NI's velocities next to ours. `build_patch.py --btn-mode`, `--enc-init` and `--pad-base` change the defaults.

### Step 0 as run on 2026-10-17 (stock firmware 1.20, macOS on Apple silicon, direct USB port)
- macOS lists *Maschine Mikro MK3* (Native Instruments, full speed, configuration 1, 480 mA allocated). Its HID driver owns interface 0; the DFU interface is free.
- `tools/usb_dump.py --image stock.bin`: the 18-byte device descriptor (`17cc:1700`, bcdDevice `0x0052`, class EF/02/01, 64-byte EP0), the 59-byte configuration descriptor (HID with EP `0x81` IN interval 1 ms and EP `0x01` OUT interval 10 ms; DFU runtime `FE/1/1` with attributes `0x09`, 255 ms, transfer size 64, DFU 1.10) and the 495-byte HID report descriptor (read from the I/O registry) are all **byte for byte in the carved stock image** (flash `0x08008d54`, `0x08008d66`, `0x08008e4d`). The device runs the firmware we analysed, and the emulator's stock baseline agrees with the real descriptors. `tools/test_usb_dump.py` pins these bytes.
- The run found a bug in `dfu_client.py`: it read the DFU *version* field (`0x0110` = 272) as the transfer size. Fixed (transfer size is bytes 5-6 of the functional descriptor) and covered by `flasher/test_dfu_client.py`; `dfu_client.py info` now prints 64.
- Live pad data (44 s of playing, 103 hits, 5 slow presses): see `docs/midi-patch.md` (*Measured pad response*) and `tools/midi_patch/fixtures/stock_pad_capture.txt`; replayed through the patched translator by `test_real_pads.py` with no stuck notes or double triggers. The first two attempts saw nothing because nothing was being touched: the stock device sends no reports at all while idle.
- Guided test of all controls (`hid_capture.py sequence`; fixture `stock_controls_capture.txt`, replayed by `test_real_controls.py`): pad numbering, the 39 button ids, encoder press/touch and the strip range (1 left .. 200 right) are as the community drivers say. One finding changed the translator: report 1 is sent only on change (the first read was already a button press, so the first press after power-up used to be swallowed as "baseline"). The encoder counter counts **up** for clockwise, as first assumed; a short-lived "inversion" came from taking the user's counter-clockwise first run for clockwise and was reverted after a clockwise-only recording (`fixtures/stock_encoder_clockwise.txt`, also replayed by `test_real_controls.py`).
- Not measured yet: current draw (needs a USB power meter), NI's MIDI-mode recording. Live data: `tools/hid_capture.py capture log.txt` listens read-only through hidapi (macOS refuses libusb the HID interface) and summarises strikes; the stock device sends nothing until something is touched, and the community driver needs no initialisation. macOS's own count is visible with `ioreg -r -c IOUSBHostDevice -n "Maschine Mikro MK3" -l | grep InputReportCount` (75 when first looked at on 2026-10-17, before any capture).
- macOS notes: `system_profiler SPUSBDataType` printed nothing inside the sandboxed session, `ioreg -r -c IOUSBHostDevice -n "Maschine Mikro MK3" -l` works; pyusb needs libusb from Homebrew and `DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib`; a control request to the HID interface fails with "Access denied" while macOS owns it.

## Step 1: stage 1 (stock image, bcdDevice 0x0051): proves the flashing path
- `python3 flasher/dfu_client.py flash work/stage1.bin` (dry run), then with `--yes-flash`. This is the first time any of our code talks to the bootloader. Expected: the device detaches, the bootloader appears as `17cc:1702`, the image downloads, the device returns as `17cc:1700` and behaves exactly like stock, now with bcdDevice 0x0051.
- Check: NI's updater now offers an update (it only does so for bcdDevice < 0x0052): that proves the recovery path. Optionally run it to put the stock image back, then repeat step 1 (a full loop).
- If the device ends up as `17cc:1702` (bootloader) after our client: wait three minutes, replug, then run NI's updater: per the updater's code a device found in DFU mode is flashed without a version check (not yet seen on hardware).

### Step 1 as run on 2026-10-17: stage 1 flashed, it worked
- Before: no NI program running, nothing but the OS had the device open (a Chrome in another macOS account, user `ju`, held a passive connection until it was killed as root; the flash command carries a guard that refuses to write while any program has the device open). Image: stock with one byte changed (flash `0x08008d60`, `0x52` -> `0x51`).
- `dfu_client.py flash stage1.bin --yes-flash`: DFU_DETACH to the runtime interface, the bootloader enumerated, all 40,392 bytes went through in 64-byte blocks, then the device reset itself. About 6 s in total. The client then died on the status poll with an I/O error: the bootloader resets the chip as soon as the image is programmed, so that is the **normal ending** (the client now treats it so, and waits for the device to come back and reports what it is).
- After: `17cc:1700`, **bcdDevice 0x0051**, descriptors byte for byte equal to the stage 1 image (`usb_dump.py --image`). So: the bootloader accepts an externally flashed, modified image (no signature or content check rejected a changed byte), our DFU client works end to end with this bootloader, and the DETACH/bootloader/DNLOAD/reset sequence needs no further steps.
- Afterwards the pads (16 hits with releases and pressure), 20 button presses, the encoder in both directions and the strip all still worked, as on stock.
- **Recovery path proven**: NI's updater (run by the user, from `proprietary/`) offered the update for 0x0051 and restored the stock firmware; the device came back as `17cc:1700`, bcdDevice **0x0052**, device and configuration descriptors equal to the stock image again. So the loop stock -> our client -> modified image -> NI's updater -> stock works on this unit. While the updater app is open it holds the device (three connections): quit it before the next flash.

## Step 2: stage 2 (same behaviour, 43 KB image): proves the bootloader accepts a larger image
- Same command with `work/stage2.bin`. Expected: identical stock behaviour (the new content is never executed).

### Step 2 as run on 2026-10-17: stage 2 flashed, accepted
- Image: 43,520 bytes (stock + bcdDevice 0x0051 + the unexecuted payload up to flash `0x0800d9ff`). Guard: nothing else had the device open. Same sequence as stage 1, 6 s, `dfu_client.py` exit status 0, device back as `17cc:1700`, bcdDevice `0x0051`. The bootloader therefore **accepts an image 3,128 bytes larger than NI's own**.
- What stage 2 cannot show: that the extra bytes were really *stored*. Nothing executes them, there is no read-back (the runtime DFU descriptor offers download only), and stage 3 runs them from the first boot instruction. A bootloader that wrote only the first 40,392 bytes would make stage 3 hang before USB (no software recovery). This is judged unlikely: the bootloader gets a raw stream with no length header and writes the blocks it receives.
- Cortex-M3 check of the payload (done before stage 3): the compiled code uses only ARMv7-M instructions (`usat`, `umull`, `ldrd`, `cbz`, `movw/movt`, `it` are all valid there; no FPU or DSP-only instruction).

## Step 3: stage 3 (the patch)
- Flash with the guarded wrapper, which refuses to write while any other program has the device open and which waits for the device to come back: `flasher/flash_guarded.sh work/patched.bin <python with pyusb>`. (On 2026-10-17 the assistant's own attempt to run this stage was refused by the auto-mode classifier as dangerous; nothing was written, and the flash was left to the user to run in a terminal, after the pre-flight checks below.) Pre-flight that was done: a fresh rebuild byte-identical to the tested image, initial SP and reset vector unchanged, exactly 24 bytes differ from stock inside the original image (the six hook sites and bcdDevice).
- **Result, 2026-10-17: stage 3 works.** The assistant's attempt was blocked by the auto-mode classifier; after the user switched the session to manual mode the same wrapper ran: all 43,520 bytes, the chip reset itself, the device came back as `17cc:1700`, bcdDevice `0x0051`, exit status 0. The device descriptor (18 B) and the 119-byte configuration read from the live device equal the bytes at flash `0x0800d800` / `0x0800d820` of the patched image, so the bootloader stored the payload and the boot hook ran; the DFU interface is number 2 and still has attributes `0x09`. macOS (CoreMIDI) lists `Maschine Mikro MK3` as a MIDI input and output. Played live (`midi_monitor.py`, 275 messages, channel 1): pads 1-9 and 13 -> notes 12-20 and 24, 16 Note On / 16 Note Off with nothing stuck, velocities 11-107, 114 poly-pressure messages (max 108); buttons -> NI's CCs (34-37, 43, 45, 47, 48, 54, 55, 58, 59, 81-91 and the spare 41, 42 for the arrows); encoder clockwise -> CC 7 rising 1..16, touch -> CC 9; strip -> CC 1 sweeping 0..127 in both directions.
- **Host to device on the real unit (2026-10-17).** The display border with diagonal ticks is drawn upright. The pad colour burst (`mmk3_host.py colors`) revealed a **race**: with the first two firmware versions a different handful of the 16 pads stayed dark each time (pads 1-4 and 8 lit; then pads 13-16 and the strip LED; then all but pads 1 and 2), while paced messages, a SysEx frame and grouped bursts always worked. The stock main loop clears the LED flag first and then reads the 80 entries; a packet arriving in the middle of that read started a fresh all-0xFF frame and wiped entries the loop had not reached. Fix: a shadow of all LED states, rewritten complete on every message. After flashing it, a burst sent during the startup animation lit all 16 pads and the strip LED (briefly, then again once the animation ended). Reproduced and fixed deterministically in `test_led_race.py`.
- Also confirmed on the unit: the button LED index map (LEDs 0, 3, 8, 14, 22, 25, 26, 29, 38 = Project, Volume, left arrow, Group, Play, Shift, Fixed Vel, Chords, Mute), the 16 pad colour names, and CC feedback brightness (127 bright, 64 normal, 20 dim; Play brightest, Stop dimmest).
- **iOS works (2026-10-17, iPad Air 4, USB-C to USB-B cable, no adapter).** No alert of any kind (so the declared 480 mA is accepted by that iPad), the startup animation plays, the apps list *Maschine Mikro MK3* as MIDI input and output, the pads play chromatically from C-1 (note 12 in the C3 = 60 naming), the touch strip drives the mod wheel. The buttons and the encoder do nothing in the apps tried: they send plain Control Changes (NI's numbers, e.g. Play 57, Rec 58, Stop 59, encoder 7) that no app assigns by default, so transport needs MIDI learn; and nothing lights up, because no app sends LED feedback for this device and the firmware has no local LED behaviour yet.
- The stock firmware plays an LED startup animation after power-up, during which pads, buttons and the encoder are ignored; the code ends it after 27 animation steps (about 1.7 s in the emulator, not yet timed on the device) and uses a 6 s countdown only as timeout (`--boot-ms` shortens the startup).
- Check afterwards: `dfu_client.py info` (the DFU interface is now number 2), `usb_dump.py --image work/patched.bin` (device, 119-byte configuration; the HID report descriptor no longer exists), `midi_monitor.py` for the MIDI messages (it needs `mido` and `python-rtmidi`).
- Flash `work/patched.bin`. Expected: the device enumerates as a class-compliant MIDI device (macOS Audio MIDI Setup / `system_profiler` shows interfaces Audio Control, MIDI Streaming, DFU). Note that the stock firmware keeps pads, buttons and encoder idle during the startup animation (about 1.7 s in the emulator, 6 s at most); the build options `--boot-ms` and `--sens` change startup delay and pad sensitivity.
- Run `tools/midi_patch/mmk3_host.py probe`, `border`, `colors` and write down: which button LED is which (index = button id, expected), the pad order, whether the display frame appears upright and not mirrored, whether the colours match the names in `docs/midi-patch.md`.
- Play the pads: note numbers (pad 1 = 12 by default, `--pad-base 36` for the GM drum layout), velocity feel, double triggers, stuck notes, pressure messages. Record raw behaviour with a MIDI monitor and compare with `test_pad_pipeline.py`'s table (hit threshold near raw 2700-3000 at sensitivity 80 is the model's prediction, not a measurement). Adjust `--sens`, `--vel-shift` and `--vel-curve` from what you see (a soft curve helps if real hits top out well below velocity 127).
- Power meter again: idle and worst case (all LEDs lit through the SysEx LED frame).
- iOS: USB-C iPad, or a Lightning iPad with a powered camera adapter; check the device appears in a MIDI-capable app and the power warning does not show. If it does, try `--max-power` lower only after the real draw is known.

## Step 8: tap tempo, clock, Note Repeat / arp, mute / solo, strum, Lock (seventh generation, built 2026-10-19, **not flashed yet**)
Why: phase 3 and the leftovers of phase 2 (`docs/native-features.md`). New in this image: the config is 259 bytes (descriptors moved up to `0x0800CF20` / `0x0800CF40`), the tick now runs a **timer-driven grid** that can emit MIDI (arp steps, clock pulses), and the USB interrupt now looks at real-time bytes (clock) coming from the host. The previous image (step 7, SHA-256 `f01badc4...a2360`, 57,766 bytes) is the one to go back to. Needs the user's go to flash (Chrome closed). Checks with the preset *Maschine-like modes* (applied unsaved):
1. Everything of steps 6 and 7 still works.
2. **Tap** four times at your tempo: the screen shows TEMPO / n BPM; **Shift + Tap** starts the MIDI clock output (MIDI Start; a MIDI monitor or an app that follows clock should show 24 pulses per beat), the Tap button blinks on the beat; Shift + Tap again sends Stop. An app that sends clock to the device (if any) takes over the tempo (EXT CLOCK).
3. **Note Repeat** on, hold a pad: the note repeats at 1/16 (screen: ARP / ON  REPEAT 1/16); **Shift + Note Repeat / Auto** change the rate, **Follow** the pattern (up, down, up-down, played, random), **Auto** the octaves; hold several pads or a chord (Chords mode) and listen to the patterns. **Lock** latches the notes; Note Repeat again switches the arp off and stops the sound.
4. **Mute**: hit a pad and it goes dark and silent; **Solo**: hit pads and only they play; **Shift + Solo** clears. Press Mute / Solo again to leave the edit mode.
5. **Notes** (strip): sliding the finger plays the 16 pad notes (or those of the pads you hold) like a strum; **Perform** goes back to CC 1.
6. **Shift + Lock** stores the encoder-target values, again recalls them (CCs jump back).
7. Hold pads and press Shift + Mute (panic) while the arp runs: everything stops.
If anything is wrong, flash the step-7 image (`prev_gen6_patched.bin` in the session scratchpad) with `flasher/flash_guarded.sh`, or restore NI's from the page.

## Chip probe: how much room is there (2026-10-18, read-only `PEEK` diagnostic, `tools/probe_chip.py`; full write-up in `docs/hardware-probe.md`)
Measured on the real device: **Cortex-M3 r1p1** (what genuine STM32F103 parts report; GD32 clones report r2p1), **flash size register 128 KB**, **no read protection** (RDP `0xA5`) and **no write protection** (WRP bytes all `0xFF`), unique ID read. Flash map in 1 KB pages: bootloader pages 0-9 (`0x08000000-0x080027FF`, 2 more blank), application from `0x08003000` through our image to `0x0800E6CC`, then **65 blank pages (65 KB) up to our save page `0x0801EC00`**, then the stock settings pages A (`0x0801F000`) and B (`0x0801F800`) and the handshake page; `0x0801F400` is blank. RAM is **not** zeroed at power-up (only the firmware's zero-initialised region is, stack included): the stack's deepest byte written so far was 448 of 1024 bytes in use (checked while probing), and the 9,704 bytes between the stack and our state (`0x20001C18-0x200041FF`) did not change in 10 s while the stock's own RAM changed 975 bytes in 2 s, so they are unused in practice. **Ceiling for "smartness"**: about 65 KB of code space (we use 5.8 KB), about 9.7 KB of RAM below our state plus 1.9 KB above, a stack with room for roughly 400 more bytes in the worst case (measured 584 of 1024 in the emulator), and CPU time: a report costs 0.7-2.2k instructions, the main loop has no hard real-time constraint beyond the pad timers (6 ms hit detector) and the 1 s watchdog. Two findings on the way: a byte-wide read of the FLASH registers bus-faults the chip (the watchdog reset the device within a second and it came back with the saved mapping intact; fixed in the source for the next flash, `PEEK` reads registers as whole words now), and DBGMCU_IDCODE read as 0 with byte access (to be read again with the fix).

## Restoring the original firmware without NI's updater
macOS has warned that NI's updater (`MM3Updater`, an Intel app) will stop working on a future macOS, so the way back to the original firmware must not depend on it. A verified copy of the stock image (the 40,392 bytes carved from NI's v1.20 updater; SHA-256 `76ebf72d...5c5917`) is kept read-only in `proprietary/MM3_firmware_1.20_stock.bin` with a `.sha256` file; keep another copy outside this folder. `tools/restore_stock.sh` flashes exactly that image with our own DFU client (it refuses any other file, then goes through `flash_guarded.sh`); the browser tool has the same as a mode and a "save a copy" button (`docs/ui.md`). From the device's side nothing is special: the bootloader took our modified images before, and it takes this one the same way. **The restore drill was run on 2026-10-18 and works**: `tools/restore_stock.sh` (exit 0, 40,392 bytes, device back as `17cc:1700` bcdDevice `0x0052`; descriptors equal to the stock image at `0x08008d54` / `0x08008d66`, HID interface 0 and DFU interface 1, no MIDI port) and then `flasher/flash_guarded.sh` with the MIDI image (exit 0, bcdDevice `0x0051`, our descriptors, protocol answering). NI's updater was not used. The same round trip was then done **from the browser page** (WebUSB) by the user: restore of the original, then the MIDI firmware again, device verified afterwards (`docs/ui.md`). Side finding: the saved mapping (flash page `0x0801EC00`) **survived both flashes**, so neither the bootloader nor the stock image touches that page; a full reflash keeps the user's mapping. Chrome (the tool page) holds the device while open and makes the guard refuse: quit it before flashing.

## Abort and recovery
- Stop the ladder at the first step that does not behave as expected; do not skip ahead.
- Not enumerating after stage 3 but the host sees nothing at all: the app likely hangs before USB comes up. No button-combination re-entry into DFU is known. This is why stages 1 and 2 exist; if it happens, stop and consider a debug probe (a hardware step outside this plan).
- Device present but misbehaving: `dfu_client.py` can detach it into DFU (the DFU interface and DFU_DETACH are kept and were verified in the emulator), then flash the stock image or a previous stage; or use NI's updater (bcdDevice 0x0051 makes it offer the stock firmware).
- The patch keeps VID:PID `17cc:1700` so NI's updater still sees the device; custom IDs are only worth it if NI's drivers interfere.
