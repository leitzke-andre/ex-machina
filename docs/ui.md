# The browser tool: mapping and flashing

`tools/ui/` is a single page (**Ex-Machina setup**) that edits the Mikro MK3's mapping (buttons to CCs, notes, MIDI Start / Stop, MMC and the device's own functions, with a second action for when Shift is held; pad notes; velocity curve and pressure; channel; encoder and strip; the LED behaviour), sends it to the device, keeps it there, and flashes the firmware. It runs entirely in the browser and talks to the device directly: Web MIDI (SysEx) for the mapping, WebUSB for flashing. Nothing is uploaded anywhere.

```
python3 tools/ui/serve.py            # serves http://localhost:8765/ and opens it   (add --mock for a stand-in device)
```
Use **Chrome or Edge** (Safari has neither Web MIDI nor WebUSB; Firefox has no WebUSB). `localhost` counts as a secure context, which both APIs need. Connect asks once for MIDI access with SysEx; the tool talks to the *Maschine Mikro MK3* port. Close other programs that use the device (a second MIDI program is fine, the NI Controller Editor and other tabs with USB access are not).

## Presets
A preset is a named, **complete configuration**. The **Presets** tab (the first one) shows every preset as a card: its name and description, the configuration in plain words (transport, pads, buttons, encoder and strip, lighting), and, when it differs from what is in the editor, the list of settings that would change. **Use** loads it into the editor and, with the device connected, sends it (it stays unsaved on the device until *Save on device*, so trying a preset is always reversible: unplug and the saved mapping is back). The header has the same switcher, and shows *modified* when the editor has drifted from the preset it was loaded from.
- **Built-in** presets come from the Python library (`builtin_presets()` in `tools/midi_patch/mmk3_config.py`, written into `mmk3_data.js` by `gen_data.py`): **Default** (exactly the firmware's values), **Maschine-like modes** (the device's own pad modes, velocity-curve selector, panic and transpose on the buttons NI prints them on, with the Shift layer), **Groove Rider 2** (tried on an iPad) and four *draft* presets made from research only, not tried yet: Korg Gadget 3, Cubasis 3, FL Studio Mobile and GarageBand (see `docs/research-sources.md`; each description says what to set up in the app). They cannot be changed or deleted, only duplicated.
- **My presets** are kept in this browser (localStorage, for this address; the page says so when the browser does not allow it). *Save as preset* keeps the editor as a new preset, *Save changes to preset* updates the one in the editor, *Discard changes* loads it again; each card has Duplicate, Rename, Export and Delete.
- **Files**: *Export my presets* and each card's *Export* write `{"format": "mmk3-presets-1", "presets": [{"name", "description", "cfg": hex}]}`; *Import* reads such files (and the older single-mapping file). A preset with the same name and the same settings is skipped; a taken name gets a number; a config from an older layout (shorter) is laid over the defaults. The command line reads the same files: `mmk3_config.py preset list [FILE]`, `preset apply NAME [FILE] [--save]`.
- A saved preset is a copy of the 259-byte config block: there is no link back to the built-in it came from. The device itself still holds one saved mapping; presets that live on the device (to switch without a computer, e.g. on an iPad) would be a firmware feature.

## What it does
- **Buttons**: for each of the 41 buttons (including the encoder's push and touch) choose what it sends: a Control Change with a number, a Note, MIDI Start / Continue / Stop, an MMC command, nothing, or one of the device's own functions (Pad Mode, Keyboard, Chords, Fixed Vel, 16 Velocities, velocity-curve / scale / chord-type step, transpose, panic, Shift, touch-strip mode, encoder target, Program Change, tap tempo, clock out, arp on / off, arp pattern / rate / octaves, latch, mute / solo pads, clear, snapshot, MIDI channel, preset slots, the step sequencer's mode / run / track select / pattern / clear / save; those with a choice show a second selector). *Show what each button does while Shift is held* adds a second row per button for its Shift action ("Same as without Shift" = nothing different; the rows show by themselves when a preset uses the layer). A button changed from what the device has shows a dot. Quick buttons for the transport only (Play, Rec, Stop): MIDI Start / Stop, NI's CCs 57 / 58 / 59, MMC.
- **Pads**: the 4x4 grid as it sits on the device with a note per pad (note names with middle C = C3, so 36 = C1), "set pads 1-16 in a row" from a first note, with quick buttons for General MIDI drums (36), NI's own notes (12), from C2 and from C3. Below it **Playing**: the velocity curve (NI's eight), the Fixed Vel value, the first note of Keyboard mode the pad-pressure mode (aftertouch per pad, channel pressure, a CC, off), the scale and chord type to start with, and the arp pattern, rate, octaves and start tempo. The **Encoder & strip** tab holds the CCs of the three encoder targets.
- **Encoder and strip**: the CC and mode of the encoder (absolute, relative offset, relative), its start value, the strip's CC and whether it sends 0 when the finger leaves; the MIDI channel, how CC buttons behave (gate, toggle, trigger), pad velocity gain and sensitivity.
- **LEDs**: the five local lighting options, pad and strip colours (17 colours), the button levels at rest and when pressed, the channel apps use for LED messages.
- **Device**: what the device reports (including the firmware name and version), the **four preset slots** in the device's flash (*Store current* keeps the active configuration in a slot, *Make active* loads one; a slot is not the power-up configuration, *Save on device* is),  "back to defaults" (not saved), "erase saved settings", and a log of what was sent.
- **Firmware**: install the MIDI firmware, or restore NI's original (below).

The header shows whether the editor matches the device (*Edited, not sent* / *On the device, not saved* / *Saved on the device* / *Device defaults*). **Send to device** makes the mapping live at once; **Save on device** keeps it across power cycles (it sends first if needed); *Send as I edit* sends every change a moment after you make it. The protocol and the saved record are in `docs/remap-protocol.md`; the page and `tools/midi_patch/mmk3_config.py` implement the same protocol.

## Flashing, and keeping the original firmware safe
The patched firmware is made **in the browser from your own copy of NI's firmware 1.20**: choose NI's updater (the `MM3Updater` file inside the app on a Mac, the `.exe` on Windows) or the 40,392-byte image, and the page finds the image in it by its SHA-256, applies `patch_bundle.json` (only our bytes: the hook instructions, the config, the descriptors, the velocity table and our code, plus the checksums of the stock and of the result; no NI code is in this repository) and checks the result against its checksum before it flashes anything. The flashing is a port of `flasher/dfu_client.py`, which flashed this device.

**The original firmware**: macOS has warned that NI's updater will stop working on a future macOS, so the restore path must not depend on it.
- *Step 1 of the Firmware tab* has **Save a copy of NI's original firmware**: a download of the exact 40,392-byte image (`MM3_firmware_1.20_stock.bin`, SHA-256 `76ebf72d33961639a0bd042ba32354dd8dc07569be69175546eb9fc06e5c5917`). Keep it somewhere safe and backed up. (A copy is also in `proprietary/MM3_firmware_1.20_stock.bin`, read-only, with a `.sha256` file.)
- The **Restore NI's original firmware** mode of the same page, and `tools/restore_stock.sh` on the command line, flash that image back. The script refuses anything but the image with that exact SHA-256 (it is tested with a stub flash script, `tools/test_restore_stock.py`). NI's updater remains an alternative as long as it runs.

Steps on the page: pick the firmware file, see the image and its checksum, *Select the Maschine…* (the browser's USB chooser), tick the confirmation, *Flash now*. A device in normal mode is switched to its bootloader first (DFU_DETACH), after which the browser needs one more click to select the bootloader device (a new USB device for it), then the image is written in 64-byte blocks and the device restarts by itself; the page waits for it to come back and shows its version.

## What is tested, and what is not
- Tested without hardware (`tools/midi_patch/run_tests.sh`): every function of the protocol layer (`mmk3.js`) against vectors made by the Python library and, end to end, the real JS client against the firmware in the emulator (SET, GET, SAVE, a power cycle, RESET); building the patched image from the stock image byte for byte (also from inside NI's real Mac updater); the DFU logic against a mock device (the same cases as the Python client's tests) and the WebUSB transport with a fake device; the page against a stand-in device in a browser.
- Verified on the real device with the Python tool (same protocol): live remapping, SAVE, reload after a power cycle, rewriting and erasing the saved record.
- **Verified on the real device with the page (2026-10-18, by the user in Chrome):** connecting over Web MIDI and applying the *Groove Rider 2* preset; afterwards the device reported exactly that configuration as active and saved (read back with `mmk3_config.py`), so SET and SAVE from the page work.
- **Flashing from the page, verified on the real device (2026-10-18, by the user in Chrome):** the page restored NI's original firmware (WebUSB chooser, DETACH, the second click for the bootloader, download) and then flashed the MIDI firmware again; afterwards the device showed our descriptors (bcdDevice 0x0051), answered the config protocol, and the saved mapping was intact. The page connected to MIDI by itself on load (permission already given) while this ran, without getting in the way. The command line (`flasher/flash_guarded.sh`, `tools/restore_stock.sh`) remains the other proven route.
