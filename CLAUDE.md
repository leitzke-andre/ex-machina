# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

The firmware is called **Ex-Machina** (version v0; `mmk3_config.FW_NAME` / `FW_VERSION`, shown on the device's idle screen). The repository is MIT-licensed (`LICENSE`), meant for git (`.gitignore` excludes `proprietary/` and every binary), with `README.md` as the entry point. Research project: make the Native Instruments **Maschine Mikro MK3** a class-compliant USB MIDI device (needed for iOS) by patching the stock firmware, with user-customisable MIDI mappings as a later goal. Hobby project. **The full patch is on the device and works** (2026-10-17: stages 1, 2 and 3 flashed with `flasher/dfu_client.py`, the device is a USB-MIDI device that macOS lists and that sent the expected notes and CCs; see `docs/hardware-plan.md`); before that the device was only read (USB descriptors, live pad/button/encoder/strip reports). It also works on an iPad Air 4 (USB-C): the apps list it as MIDI input and output and the pads play. Verified by eye: LED and display feedback, cold boot. The third generation (pad 1 = note 36, Play/Stop as MIDI Start/Stop, local press/hit LEDs) is flashed and plays; its resting LEDs were wiped by the stock startup animation, which a main-loop hook now fixes (built and emulator-tested, to be flashed). The fourth generation (run-time remapping over SysEx, saved to a flash page, `docs/remap-protocol.md`) is flashed and verified on the device (2026-10-18). The browser UI for mapping, presets and flashing/restoring (`tools/ui/`) works on the device. The fifth generation (the controller's own functions: Pad Mode / Keyboard / Fixed Vel / 16 Velocities / velocity-curve selector / transpose / panic, a Shift layer, pad pressure options and temporary screen messages; `docs/midi-patch.md`, step 6 of `docs/hardware-plan.md`) is **flashed (2026-10-18) and the screen messages work on the device**. The sixth generation (phase 2: 24 scales, Chords mode with five chord types, strip modes Pitch / Mod with an LED bar, encoder targets, Program Change; step 7 of `docs/hardware-plan.md`) is **flashed (2026-10-19), protocol verified, the playing checks are the user's**. The seventh generation (phase 3: tap tempo, MIDI clock out / in, Note Repeat and arp with six patterns, mute / solo pads, strip strumming, Lock snapshot; step 8 of `docs/hardware-plan.md`) is **flashed (2026-10-19), protocol verified, the playing checks are the user's**. The eighth generation (**Ex-Machina v0**: the screen drawn from state with the EX-MACHINA / V0 idle screen and a status line, the MIDI channel selector, four preset slots in flash, a step sequencer with a grid on the screen; step 9 of `docs/hardware-plan.md`) is **flashed (2026-10-20), protocol verified, the playing checks are the user's**. Open: current draw (no power meter), swing / metronome click, the USB product string (still NI's "Maschine Mikro MK3"; changing it would rename the device in apps). Everything else is static analysis (Ghidra), emulation (Unicorn) and community/NI documentation. Read in this order: `docs/midi-patch.md` (design, defaults, tests, open risks), `docs/firmware-notes.md` (reverse-engineering findings), `docs/research-sources.md` (what each source confirmed), `docs/hardware-plan.md` (staged flashing plan for when the device is connected), `docs/native-features.md` (NI's own controller functions that the MIDI firmware could reproduce, with effort and an order), `docs/hardware-probe.md` (what the chip is and how much flash/RAM/stack/CPU room the firmware has, measured on the device), `docs/remap-protocol.md` (the SysEx configuration protocol), `docs/ui.md` (the browser tool).

## Inputs and what must stay local
- `proprietary/` holds NI's manual, cheat sheet, firmware updaters (v1.20, Mac and Windows) and the Controller Editor 2.8.2 installer image. Treat all as read-only; never run the updaters (they flash hardware) or the installer, and never mount or install the editor: it was opened with 7-Zip only (`7zz x`, then `xar`/`gunzip | cpio` on the package payloads) into the session scratchpad. Plain data files (templates), documentation and symbol/string metadata were read first; the user then explicitly authorised analysing NI's binaries (nothing installed, personal curiosity) and added a permission rule, so the editor's host-side MIDI engine was decompiled with Ghidra (static only, x86_64 slice, output in the scratchpad; behavioural findings only in `docs/research-sources.md`). A follow-up lookup of the velocity-curve function was first refused by the auto-mode classifier; the user then left auto mode and asked for a retry, which worked (NI's default curve is Linear). If a classifier denial happens again, do not work around it: it is the user's call.
- NI's firmware is proprietary: the carved image, decompressed RAM data, patched images and Ghidra decompilations stay out of the repo (session scratchpad only). The repo holds scripts, notes, our patch source and tests. One exception, at the user's request (NI's updater will stop running on future macOS): a read-only, checksummed copy of the unmodified stock image, `proprietary/MM3_firmware_1.20_stock.bin` (SHA-256 `76ebf72d...5c5917`), so that `tools/restore_stock.sh` can put the original firmware back without NI's updater; `proprietary/` is excluded by `.gitignore` like the other NI inputs, and `tools/ui/patch_bundle.json` holds only our bytes and checksums.

## Commands
- Carve the stock image: `python3 tools/carve_fw.py <MM3Updater binary> stock.bin` (40,392 bytes at Mac file offset `0x22d570`).
- Build and run everything: `tools/midi_patch/run_tests.sh stock.bin workdir` (needs clang with the ARM target and `pip install unicorn pyelftools usb-protocol`; set `PYTHON` to a venv interpreter).
- Single suite: `python3 tools/midi_patch/test_<name>.py patched.bin data_init.bin` (`test_translate`, `test_patch`, `test_features` (transport/button actions, local LEDs, output bounds), `test_display_race` (host display regions injected at every point of the firmware's display writes), `test_phase4` (channel, preset slots with power-cut sweeps, the step sequencer and its grid, the idle screen), `test_phase3` (time-based: tap tempo, clock out / in, arp, mute / solo, strum, snapshot), `test_phase2` (scales, chords, strip modes, encoder targets, Program Change), `test_modes` (the controller's own functions: pad modes, shift layer, curve log with power-cut sweep, panic, pressure, mode LEDs, display messages compared pixel by pixel), `test_config` (run-time config: SysEx protocol, saved record, power cuts) and `test_mmk3_config` (host library + CLI against the emulated device), `test_startup` (takes `patched.bin stock.bin data_init.bin`: the real startup animation, patched vs stock), `test_enumeration`, `test_pad_pipeline`, `test_led_race` (an LED burst interleaved with the real stock main loop at random instruction offsets), `test_real_pads` and `test_real_controls` (replay `tools/midi_patch/fixtures/stock_pad_capture.txt` and `stock_controls_capture.txt`, real reports of the stock device, through the shared `replay.py`), `stack_depth`); `test_vel_curve.py` takes `stock.bin data_init.bin workdir` because it runs `build_patch.py` itself; `flasher/test_dfu_client.py` needs no firmware.
- Read-only device check (stock or patched): `DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib python tools/usb_dump.py --image stock.bin` and `flasher/dfu_client.py info` (venv with pyusb, libusb from Homebrew); `tools/test_usb_dump.py` needs neither. Live pad/button/encoder/strip capture from the STOCK device (read-only, hidapi): `python tools/hid_capture.py capture log.txt` (waits for the first touch, then prints a summary: note-on values per strike, pressure, buttons); `tools/test_hid_capture.py` needs no hardware.
- Browser tool (mapping, flashing, restoring): `python3 tools/ui/serve.py` then Chrome/Edge, see `docs/ui.md`; its checks run inside `run_tests.sh` when `node` is installed (`tools/ui/test_mmk3.mjs`, `test_flash.mjs`, `test_presets.mjs`; `gen_data.py`, `make_vectors.py`, `make_bundle.py` regenerate the data the page uses, `--check` fails when it is stale). Restore NI's original firmware: `tools/restore_stock.sh`.
- Remapping a flashed device: `python tools/midi_patch/mmk3_config.py info|get|set|button|pad|save|reset` (mido + python-rtmidi; protocol in `docs/remap-protocol.md`; the emulator tests share the harness `tools/midi_patch/devsim.py` and the flash model `tools/emu/flash_model.py`).
- Flashing: `flasher/flash_guarded.sh image.bin <python with pyusb>` (guard + `dfu_client.py flash --yes-flash`; `flasher/` is the self-contained DFU client / WebUSB port with its own README, PROTOCOL.md and tests `flasher/run_tests.sh`; it may later move to its own repository, so it must not import anything from the rest of the repo); listening to the patched device as MIDI: `python tools/midi_monitor.py` (mido + python-rtmidi).
- Build options: `build_patch.py stock.bin out.bin [--stage 1|2|3] [--vid --pid --bcd --max-power --sens --boot-ms --pad-base (default 36) --transport realtime|cc|mmc --local-leds on|off --pad-colour --strip-colour --enc-mode --enc-init --btn-mode --vel-curve --vel-table --vel-shift]`.

## Key facts
- Firmware: Cortex-M3, STM32F103RB class (128 KB flash, 20 KB RAM), flash base `0x08003000`, bootloader below it (not available), ST USB-FS-Device library, Keil toolchain with an RLE-compressed `.data` (`tools/decompress_data.py`). Flash pages `0x0801F000`/`0x0801F800` hold settings, `0x0801FC00` is the bootloader handshake page.
- Ghidra headless (Homebrew 12.1.4) has no PyGhidra: write helper scripts in Java (`tools/ghidra/`). Import raw, `ARM:LE:32:Cortex`, base `0x08003000`; run `Dis.java` first (auto-analysis finds few functions).
- The emulators need the decompressed `.data`; per-pad SysTick counters must be simulated when running the pad routine (`tools/midi_patch/test_pad_pipeline.py` does it with the real SysTick handler). `tools/emu/usb_model.py` models the STM32 USB peripheral well enough for the real USB library to enumerate; its baseline check is `tools/emu/enumerate_stock.py`.
- Patch hooks are seven `bl`/instruction replacements (the seventh, in the main loop, re-applies the LEDs when the stock startup ends and is where deferred work such as flash writes belongs) plus new flash content from `0x0800CE00` (259-byte config, descriptors, nine 256-byte velocity tables, a 5x7 font, the display texts and the scale masks, code last; the layout constants live in `build_patch.py` and the tests import them; texts are data in flash because the object may have no `.rodata`, their order is the `T_*` enum of `translate.c`); the config block layout in `translate.c` (`struct cfg`, size asserted) is mirrored in `build_patch.py`. The config is a RAM copy (defaults, or the record saved in flash page `0x0801EC00`) edited by SysEx; translator/LED/request state is RAM at `0x20004200` (`ST_ADDR` in `translate.c`, `build_patch.py` reads it from there). Defaults of the current build: pad 1 = note 36, Play/Stop = MIDI Start/Stop, local LEDs on. The fifth generation adds the controller's own functions as button actions (Pad Mode / Keyboard / Fixed Vel / 16 Velocities / velocity-curve step / transpose / panic / Shift), a shifted second action per button, pad pressure modes, and screen messages written from the main loop (`docs/midi-patch.md`); the curve choice lives in an append-only log in the second half of the save page. Run-time modes are not part of the config and reset at power-up and on every SET.
- Stock updater facts that constrain the patch: it only offers an update when bcdDevice < `0x0052` and only recognises VID:PID `17cc:1700` (DFU mode `1702`); keep both for restorability.
- Do not flash anything beyond what the user has explicitly approved, one stage at a time (`docs/hardware-plan.md`); `flasher/dfu_client.py` is dry-run by default, worked for stage 1, and its flash command must only run with nothing else holding the device (check `ioreg ... IOUserClientCreator`). NI's updater, run by the user, is the restore path.
